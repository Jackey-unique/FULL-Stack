# COM661 CW1 高分审查报告

审查日期：2026-10-27（Asia/Shanghai）。审查对象：当前工作目录中的源码、原始计划、原始评分文件及现有提交 ZIP。

## 一、结论

项目具有冲击 First Class 的技术基础：并非只替换 Biz Directory 的字段，已具备双嵌套资源 CRUD、四个 Blueprint、真实 MongoDB 聚合、权限与作者检查、JWT 撤销、管理员审批、数据导入和并发条件更新。

但是，目前不能把“后端做完了”视为“80+ 提交已准备好”。优先缺口是提交证据、接口文档的完整性，以及统计功能与研究用途之间的贴合程度。若只继续美化浏览器界面，提分收益可能低于补齐这些部分。

本报告没有修改业务代码、真实研究数据、演示数据或原有提交压缩包。它是审查结果及优化建议，不是评分承诺，也不是代填的自评表。

## 四、优先级 P0：提交前必须完成

### 1. 补齐必交材料，尤其是 5 分钟视频

现有提交目录只有两个 ZIP。README 与设计文档明确指出视频、独立 PDF、自评表留待学生准备。此前排除这些文件只是开发范围选择，不会免除课程提交要求。

按 Specification 第 2–3 页，至少逐项核对：

1. 后端代码 ZIP。
2. 每个 MongoDB collection 通过 mongoexport 导出的 JSON ZIP。
3. 不超过 5 分钟的视频：介绍用途/数据、Postman 使用演示、代码 walkthrough。
4. 分别提交的四类 PDF：完整后端代码、全部 endpoint 汇总、Postman 自动测试运行结果、Postman 生成的 API 文档。
5. 填好的自评表。
6. AI 使用所需的 Design and Development 材料及真实完整聊天记录。

Specification 明确说缺少代码或视频会严重影响获得高分的可能性。因此不能把缺视频理解为“只少拿 Submission Package 的一点分”。

Postman 公开文档 URL 是 Clinic 建议的便利方式，并非必须公开发布。按主 Specification 准备要求的 PDF，并视需要提供 URL；不用为了 URL 公开研究数据或真实凭据。

建议视频时间分配：用途与数据 30 秒；Postman 主/子资源闭环和鉴权失败 100 秒；聚合与筛选 45 秒；复杂代码解释 95 秒；测试与限制 20 秒。总计约 4 分 50 秒。应由学生用自己的话讲解，并根据实际操作排练。

### 2. 把 AI 披露从摘要补成可核查材料

`docs/DESIGN_AND_AI.md` 已较诚实地说明帮助范围，但它自己也明确“不是完整聊天记录”。需要导出实际 prompts 和 responses，附到最终设计开发材料。

尤其要能解释：

- 为什么按 subject + session 合并，而不是只按 subject。
- 为什么 notes/analyses 嵌入，而 users 独立，何时应改用独立集合。
- visibility 如何同时约束详情、列表、统计和导出。
- latest-per-modality 和 paired-only 聚合的每个阶段。
- JWT 的 jti、TTL 与 auth_version 分别解决什么问题。
- 版本条件更新能阻止哪些并发覆盖，以及它没有实现浏览器长期持有旧版本时的条件更新协议。

不要用这份报告或设计摘要冒充原始聊天记录。

### 3. 明确最终提交的数据与应用用途

原计划标题包含“Diagnostic Support”，当前实际实现是研究元数据与外部预计算结果管理，并不执行 MRI 推理。原计划把估计年龄写成“Where suitable ... available”的条件功能，因此不能简单认定没有模型就违约，也无需临时训练模型来凑功能。

但最终标题、视频和自评必须围绕实际用途统一，例如“BrainAge Connect — Infant MRI Metadata and Precomputed Result Management”。解释这是一套可管理、比较用户提供结果的研究后端，避免让老师期待临床诊断或 MRI 上传即预测。

提交数据是 150 条合成记录，而真实本地导入是 558 条会话。原始 Clinic 允许合理合成数据，因此合成数据本身不应被判作不合格。需要说明：提交 ZIP 为什么采用合成演示；真实数据做过哪些准备；哪些统计数字属于哪个库。不得把真实库数量或 MRI 文件属性套在合成提交库上。

为 15% 数据集项准备一份可分享的数据准备证据：来源链接、subject/session 匹配示意、字段类型表、一份明确标注合成的嵌套样例、缺失/冲突处理规则。若展示真实导入统计，应使用不包含受试者详情、私有本机路径或受限文件内容的摘要。

## 五、优先级 P1：最值得做的代码和文档优化

### 4. 完善 Postman 文档和响应示例

证据：`postman/BrainAgeConnect.postman_collection.json` 中 48 个 request 没有保存任何 response example；多数 description 只是编号、名称和期望状态码。

影响：Clinic 第 8 页要求全 endpoint、参数和返回值有清晰说明，并用 examples 解释。现有 `docs/API.md` 有帮助，但无法自动让 Postman 生成的文档达到同样完整程度。

建议：按 Auth、Samples、Notes、Analyses、Statistics、Admin 分组；保留可按顺序执行的 runner 顺序或另设 lifecycle 集合。每个接口说明用途、权限、参数含义/范围、默认值、请求体和返回字段。保存成功响应范例，并为关键接口增加 400/401/403/404/409 范例。

验收：只把集合交给一个不了解项目的人，他能登录、创建记录、运行复合筛选、读懂聚合结果并处理错误，不需要翻源码。所有示例均用合成数据、占位 JWT，不复制真实响应凭据。

### 5. 补齐 OpenAPI 成功响应契约

位置：`scripts/generate_openapi.py:56`。生成器基本只写 Success 描述，错误 schema 比成功响应更完整。

建议增加 UserPublic、SampleSummary、SampleDetail、Note、Analysis、Pagination、各类 Statistics 等 schemas，为所有返回 JSON 的 200/201 明确结构。明确 null、ObjectId 字符串、日期、单位和源分组。DELETE/logout 的 204 保持无响应体；CSV 正确标注 MIME 类型和列。

这能提升 API 设计与文档质量，也可展示同一后端能够支持独立第三方前端。不要只在 JSON 成品补字段而不修改生成器，否则重新生成会丢失改动。

### 6. 统计按 method/model_version 分层，避免混合不可比结果

位置：`brainage/analytics.py:25`、`:36`。当前“最新结果”按样本和模态选择；成熟度最后只按 source/modality 分组；配对比较只按 source 汇总。method、model_version 虽有保存，却未用于筛选/分层。

具体问题：同一模态中方法 A 与方法 B 的结果可能进入同一个均值；比较还可能把 dMRI 某版本与 fMRI 另一个不匹配的版本配对。API 文档承认这些结果只是探索性汇总，但对声明的研究比较用途仍有限制。

建议优先提供 method/model_version 筛选，或明确的模型配对参数；按选定模型范围筛选后再选择每条样本的最新结果。不能先选“任意模型最新”再过滤，否则会错误丢弃仍有目标模型结果的样本。返回所选规则、结果数量和排除数量，保留来源隔离和可见性过滤。

验收：构造同一条样本的旧 A-v1 和新 B-v2 结果；查询 A-v1 应取旧 A-v1。不同模型版本不会静默合并；配对仅纳入满足所选双方条件的样本。

这是比新增一堆通用 CRUD 更有针对性的复杂功能，也更贴合 80+ 对应用特色与额外研究的要求。

### 7. 补上“按年龄组汇总成熟度指标”

原计划明确提到此功能。目前 `cohort_rows()` 有年龄分组和数量，但 `maturity_rows()` 的估计年龄/差值均值没有按年龄组汇总。两者同时存在不等于已经完成“按年龄组的成熟度汇总”。

建议把年龄组纳入 maturity 聚合的可选 group_by，或扩展现有统计接口；同时保留 source、modality 和模型范围。年龄未知单列 unknown；输出总结果数和具有参考年龄的有效差值数，避免 `$avg` 跳过 null 后，显示的 sample_count 被误认为均值分母。

验收：至少覆盖不同年龄组、边界 32/37/42、未知年龄、历史重复分析、其他用户私有记录。数量和均值用固定小数据独立手算核对。

### 8. 加强测试的“证据质量”，尤其是 Postman 返回值断言

当前 51 项 pytest 包含参数化展开，并非 51 个完全独立的业务流程；48 个 Newman 请求中的不少断言只检查 HTTP 状态。它们是有效基础，不能等同于覆盖所有 endpoint 的所有退出路径。

建议针对高价值边界补测试：

- Postman 主/子资源更新后 GET 并检查字段值，删除后检查 404，错误请求后确认没有写入。
- 验证分页内容和顺序、聚合数值、来源分组、导出的列与行，而不只是 200。
- 年龄组边界、null、空数据集、配对缺一侧、相同创建时间的稳定选择。
- 嵌套资源的重复/未知参数、空 PATCH、类型范围、200 条上限。
- 过期/失效 token、非所有者、跨父资源 ID、导入字段只读。
- 413 过大请求体及受控数据库异常的 503，不通过破坏真实库来测试。

本轮复测只运行了现有用例，没有声称这些额外场景全部已覆盖。若想展示覆盖率，可再测行/分支覆盖并附未覆盖解释，但 rubric 没规定必须达到某个百分比。

最终公开证据应是脱敏摘要、Postman Runner 截图和要求的 PDF；原始 Newman JSON 可能包含认证头和 token，不直接进入提交包。

## 六、优先级 P2：冲 80+ 的补强项

### 9. 用实际 explain 说明索引的效果

`brainage/__init__.py:15` 已创建索引，但没有查询计划或性能比较证据。索引存在不等于所有组合筛选和排序都获益。

选 2–3 个真实使用场景：样本代码精确定位；来源 + 年龄范围；研究员可见性 + 排序。记录 explain 的 winningPlan、totalDocsExamined、totalKeysExamined、nReturned，解释是否出现 COLLSCAN 或内存排序。只有证据证明有必要时再添加复合索引。

无前缀的字面子串 regex 仍可能扫描；这在几百条记录上不一定是性能问题，应如实解释。不要为了展示“复杂”而加入与婴儿 MRI 无关的地理位置查询。

### 10. 完成从提交 ZIP 出发的复现验收

本机能跑依赖当前 `.venv`、便携 MongoDB、环境配置和本地路径；这些并未全部打包。代码包与工作文件一致，不等于在老师电脑上解压即能用。

建议在独立目录中只用两个提交 ZIP：创建全新虚拟环境；安装依赖；配置随机 JWT secret；安装/启动 MongoDB 和 Database Tools；解压/恢复数据库；运行 API；登录、列表、一个聚合、Postman；记录明确命令和预期结果。

README 应明确 Database Tools 的安装要求、数据 ZIP 解压目录，以及恢复数据库后实际启动时应使用的 MONGO_DB。现有 START 脚本固定选择真实/演示库，恢复到其他名字应按文档直接运行 app.py 或显式支持该配置，不能只改 `.env` 后继续点固定启动器。

`scripts/run_postman.py` 还假设 newman 在项目 tools 路径，Node 的备用路径是 Codex 本机路径。复现说明应给出普通 Node/Newman 安装方式，或让 runner 优先查找通用可执行文件；不应要求评分者装 Codex。

本轮没有做上述全新环境安装验收，因此不把它报告为已通过。

### 11. 让提交证据与最后一版完全一致

`scripts/package_submission.py:17` 采用显式文件列表。新增交接文件、本报告和未来的证据文件不会自动被包含；如确需随代码包交付，按用途加入白名单。

目前 ZIP 内源码与本地对应文件一致，这是正面结果。后续任何修改完成后，要按“测试 → 生成文档 → 导出合成库 → 打包 → 检查 ZIP”的顺序重新做一遍，不能提交旧 ZIP 并引用新测试结果。

保留四个 collection 的 mongoexport 文件，包括空 collection；可在演示操作后导出有代表性的合成审计记录，但不需要为了数量伪造日志。原始评分表不要求每个 supporting collection 必须非空。

### 12. 可选的实现打磨

- 把密集的单行条件/分号语句拆开，给复杂聚合中间结果添加字段说明，帮助代码 PDF 阅读与 walkthrough；避免改变已经稳定的行为。
- 若要声称支持客户端长期编辑冲突，增加 If-Match/ETag 或客户端版本条件。现有版本机制主要防止服务器端重叠写入，不能直接拒绝用户几分钟前读到旧数据后的普通 PATCH。
- 浏览器空筛选结果时，当前 source 提示可能显示 LOCAL RESEARCH DATA，即使运行的是合成库；如果后续要展示浏览器，应从稳定环境标识判断，而非只根据当前筛选结果。CW1 首先考核后端，这属于次要界面修整。
- 登录限流、TLS、远程数据库认证属于部署增强。当前本机课程环境不必为了这些扩大项目范围，若宣称多人生产部署则另行处理。

## 七、推荐执行顺序

1. 先明确最终用途与合成提交数据说明，列齐所有必交材料。
2. 补齐 Postman 的参数说明、成功/失败响应范例及关键业务值断言。
3. 补齐 OpenAPI 成功响应结构。
4. 实现按模型筛选/分层和按年龄组的成熟度汇总，配固定数据验证。
5. 选取查询做 explain，并完成从 ZIP 出发的复现。
6. 脱敏整理测试证据，完成四类 PDF、AI 完整记录和学生自评。
7. 学生排练并录制 5 分钟视频，重新生成并核查最终两个 ZIP。

当前不建议临时加入 MRI 模型训练、完整 Angular 前端、云部署或无关的数据库特性。它们不是现有高分缺口的最短解决路径，还会挤占测试和演示准备时间。

## 八、怎样判断优化完成

完成后应当能让评分者仅依靠提交包：独立启动系统；通过 Postman 完成主/子文档 CRUD 与失败路径；看懂有模型和年龄分层的聚合；找到真实的测试通过证据；理解真实与合成数据边界；通过学生讲解判断其掌握复杂实现。

达到这些可检查的结果，才比单纯增加接口数量或页面装饰更接近 rubric 的 80+ 描述。
